# PRD：个人 AI 工作台——PMS 日报集成

## 1. 摘要

将现有“AI 用量看板”扩展为本地优先的个人 AI 工作台。第一阶段把 Git 日报能力与 PMS 日报接口整合进桌面应用：从已关联的本机 Git 项目采集提交记录，生成日报正文，由用户选择 PMS 项目、任务和工时后直接提交。

产品继续以 AI 工具、开发项目和工作产出为中心，不扩展为通用待办、日历或笔记软件。

## 2. 联系人

| 角色 | 人员 | 关注点 |
| --- | --- | --- |
| 产品负责人 | 魏鹏程 | 确认工作流、报告格式和发布范围 |
| 设计与开发 | 魏鹏程 / Codex | 保持现有桌面看板的本地优先体验，并完成集成 |
| 使用者 | 重度使用多种 AI 编程工具的个人开发者 | 快速了解 AI 资源，并低成本完成工作复盘和日报 |

## 3. 背景

当前 `xlt-workbench` 已统一展示 Codex、火山方舟、Kiro、Qoder 等平台的订阅额度、Token 使用量和成本信息。它解决了“AI 还能不能继续用”的问题，但没有覆盖“今天完成了什么”，也不能直接完成 PMS 日报填报。

独立的 GitReport 项目已经能从多个本机 Git 仓库读取提交记录，调用 AI 生成日报/周报。PMS 已提供待填日报、当日可选项目和任务、日报详情，以及新增或更新日报的接口。两个项目的用户、数据边界和本地运行方式高度一致，但目前需要在多个页面之间切换，并手工完成项目、任务和工时分配。

本次集成的机会是：以“今天的 AI 用量 + 今天的代码产出 + 一键复盘”为一个完整闭环，将看板升级为真正可每天打开的个人 AI 工作台。

## 4. 目标

### 产品目标

在一个桌面应用内完成以下日常流程：查看 AI 用量，读取今天的 Git 工作，生成日报正文，操作式分配 PMS 项目/任务/工时，然后直接提交。

### 业务价值

- 减少在用量看板、Git 日志、日报网页之间切换的次数。
- 让日报基于真实提交记录生成，减少遗漏和重复回忆。
- 让 AI 消耗与实际工作产出能在同一处回顾，帮助判断订阅和工具的价值。
- 保持数据与代码路径留在本机，避免把 Git 历史上传到额外的中间服务。

### 关键结果

在首个正式版本发布后的四周内，面向产品负责人本人验证：

1. 100% 的日报可在工作台内从选定 Git 项目生成，无需启动独立 GitReport 服务。
2. 从进入“日报”页面到提交一份 PMS 日报，常规流程不超过 3 分钟。
3. 每周至少 4 个工作日使用工作台生成并提交日报。
4. 用户可为一天添加多个项目和任务条目，并独立填写每项的正常工时与加班工时。

## 5. 用户与使用场景

### 主要用户

使用多个 AI 编程产品、同时维护多个本机 Git 项目的个人开发者。

### 核心任务

| 场景 | 用户想完成的事 | 成功标准 |
| --- | --- | --- |
| 下班前复盘 | 知道今天在哪些项目完成了哪些工作 | 能看到按项目归类的提交列表和数量 |
| 撰写日报 | 将提交信息整理为可提交的自然语言日报 | 一次生成后只需少量编辑 |
| 分配工时 | 将当天工作分配到 PMS 的项目和任务 | 可自行增加多个条目并填写每项工时 |
| 资源回顾 | 对照 AI 用量与当日产出 | 概览页可同时看到用量摘要、提交数和最近日报 |
| 提交日报 | 将配置完成的条目直接提交到 PMS | 提交后可看到 PMS 返回的结果 |

### 约束

- 用户的 Git 仓库分散在本机多个目录，且可能含中文路径。
- Git 作者可能有多个姓名或邮箱，需要支持多作者过滤。
- 用户可选择不同 AI 服务商和模型，密钥仅在本机使用。
- PMS 的项目、任务和工时类型由当天接口结果决定，不能在应用内自行编造。

## 6. 价值主张

个人 AI 工作台不是“再做一个日报工具”，而是将 AI 工作过程连接起来：

| 用户痛点 | 工作台提供的价值 |
| --- | --- |
| 看得见额度，却说不清今日产出 | 在同一应用里连接用量、提交和报告 |
| Git 提交碎片化，日报靠回忆 | 从真实 Git 记录生成按项目归类的初稿 |
| 独立日报服务需要启动、浏览器访问和重复配置 | 直接作为桌面端工作区的一部分使用 |
| 项目、任务和工时依赖手工在 PMS 页面填写 | 在工作台中加载 PMS 当日可填选项，并以条目形式分配 |
| 多项目工作容易漏填或工时分错 | 每个条目单独选择项目、任务、工时类型、正常工时和加班工时 |
| 复制日报后还要切回 PMS 提交 | 生成后在同一工作区直接提交 PMS |

相较于通用笔记或待办产品，本产品的优势是读取本机 AI 工具与 Git 项目产生的真实数据，并以低干扰方式完成工作复盘。

## 7. 方案

### 7.1 信息架构与用户流程

现有侧栏新增“日报”工作区；概览页新增“今日工作”卡片。

```text
概览
├─ AI 用量摘要
├─ 今日工作：已关联项目数、今日提交数、最近日报
└─ 快捷操作：生成日报

日报
├─ Git 工作：日期、作者、代码项目、提交预览
├─ 今日正文：生成和编辑 Git 提交摘要
├─ PMS 工时条目：项目、任务、工时类型、正常/加班工时
├─ 明日计划：自动与今日正文保持一致
└─ 提交：直接发送到 PMS 并显示结果
```

主流程：

1. 用户在“日报设置”中关联本机 Git 项目，并设置常用作者。
2. 用户从 PMS 待填写日报中选择日期。
3. 应用读取 `git log`，展示提交预览和数量；用户点击“生成今日工作”。
4. 应用查询 PMS 当日可选项目、任务和工时类型。
5. 用户添加一个或多个工时条目，为每个条目选择项目、任务、工时类型、正常工时和加班工时，并填入对应的今日工作内容。
6. 应用将每个条目的今日内容原样写入对应的明日计划，无需额外填写。
7. 用户点击“提交日报”，应用调用 PMS 保存接口并展示提交结果。

### 7.2 第一阶段功能需求

#### A. Git 项目与作者管理

- 用户可以添加、移除、选择本机 Git 仓库。
- 用户可选择一个目录，扫描其下最多四层目录的 Git 仓库，再批量添加。
- 每个项目显示名称、绝对路径和当前分支。
- 用户可以保存多个 Git 作者姓名或邮箱；生成时支持临时覆盖。
- 项目配置在当前工作台统一保存，不再依赖独立 GitReport 的运行配置。

验收标准：添加有效 Git 路径后能显示仓库名和分支；选择多个项目和作者后，后续打开应用仍能恢复选择。

#### B. Git 提交采集与预览

- 支持日报（默认当天）和自定义单日补报日期。
- 采集所有分支的非合并提交，输出提交哈希、时间和消息。
- 提交预览按项目分组，显示每个项目的提交数量。
- 无提交时明确提示所选日期范围、项目和作者条件。
- Git 命令在 Tauri 后端执行，前端不直接执行本机命令。

验收标准：对至少三个本机项目、含中文路径的项目和多个作者过滤条件，采集结果与等价 `git log` 命令一致。

#### C. 今日工作生成与编辑

- 首期支持 MiniMax、Kimi、DeepSeek 三个 Provider，并显示可选模型。
- 生成前将项目名、提交列表、报告类型和日期范围传入统一 Prompt。
- 日报输出为精炼的编号工作项。
- 生成结果必须可在应用内编辑，编辑后的文本作为最终保存内容。
- 日报正文只基于 Git 提交生成；不要求填写会议、沟通或其他非 Git 工作。

验收标准：一份包含多个项目和相似提交的输入，生成后按项目语义合并为不超过 30 字的工作项；用户编辑后的内容将作为 PMS 条目描述提交。

#### D. PMS 工时分配与提交

- 用户选择某个待填写日期后，应用调用 PMS 接口读取可填写的项目、任务和工时类型。
- 工时分配区以“条目卡片”呈现；用户可以添加或删除条目。
- 每个条目包含：项目、任务、工时类型、今日工作描述、固定正常工时和加班工时。
- 选择项目后只显示该项目的任务；选择任务后只显示该任务允许的工时类型。
- 正常工时固定为 7 小时；用户只需确认项目、任务和加班工时。页面展示当天工时总计。
- 用户可把 AI 生成的一个或多个工作项关联到当前条目；关联项自动合并为该条目的今日工作描述，仍可手动修改。
- 每个条目的明日计划始终使用该条目的今日工作描述，不提供单独编辑入口。
- 点击“提交日报”后，应用组装 `entries` 和 `tomorrowPlanPaperEntries`，调用 PMS `addOrUpdate` 接口，提交值固定为 `true`。
- 提交后显示 PMS 返回的结果，并刷新当月日报状态。

工时分配操作：

1. 用户点击“添加工时条目”。
2. 在条目中依次选择 PMS 项目、任务和工时类型。
3. 从“今日工作”中勾选属于该条目的 AI 工作项；可勾选多项，也可直接修改汇总后的正文。
4. 手动填写该条目的正常工时和加班工时；页面仅显示总计，不代替用户调整。
5. 重复添加条目，直到当天所有项目都分配完成；点击“提交日报”直接发送。

验收标准：用户可为一个日期添加多个条目，选择不同项目和任务，并为每项填写加班工时；提交后的字段与界面输入一致，正常工时总计为 7 小时。

#### E. PMS 日报状态与日期选择

- 用户可按月读取 PMS 日报列表，并选择未填或需补填的日期。
- 进入日期后，应用读取节假日类型和该日的 PMS 日报详情。
- 该版本不自动处理节假日、无提交、多日补报和加班情形；用户自行决定是否填写、选择日期和填写工时。
- 该版本不提供草稿保存；用户完成配置后直接提交。

验收标准：选择有效待填日期后，能加载对应可选项目和任务；没有 Git 提交时，用户仍可自行决定是否填写并提交。

### 7.3 技术方案

#### 应用内集成

- 不嵌入或启动独立 Express 服务，不使用 iframe。
- 新增 `DailyReportService`，负责聚合 Git 数据、AI 生成、PMS 日报数据和提交流程。
- 新增 `src-tauri` 命令：Git 仓库验证、目录扫描、日志采集、PMS 当月列表、日期详情、可选项目/任务、日报提交。
- 延续现有连接器模式：前端通过 `invoke` 调用 Tauri command；Rust 负责受控运行本机 `git` 命令。
- 新增 Vue 页面与组件：`DailyReportView`、`GitProjectPicker`、`GitCommitPreview`、`PmsEntryEditor`、`TodayWorkComposer`、`TodayWorkCard`。

#### 数据模型

```ts
type GitProject = {
  id: string
  name: string
  path: string
  branch?: string
}

type PmsDailyEntry = {
  projectId: string
  taskId: string
  workType: number
  description: string
  normalHours: number
  addedHours: number
}
```

- PMS Token 及同次浏览器会话的 Cookie 由用户手动粘贴，仅保留在当前应用会话；`application` 与 `usertype` 等非敏感接口配置与普通偏好分开保存。
- Git 原始提交仅用于本机预览与模型调用；报告不自动上传到任何服务。

### 7.4 非目标

- 不构建通用待办、日历、知识库或笔记系统。
- 不开发 macOS WidgetKit 系统小组件。
- 不做团队协作、云端账号、多人报告汇总或远程 Git 平台同步。
- 不替用户判断应选择的 PMS 项目和任务，也不替用户填写加班工时。
- 不自动处理节假日、无提交、多日补报或加班；这些情况由用户手动决定。
- 不提供草稿保存；日报由用户主动点击后直接提交。
- 不在第一阶段统计 IDE 内的非 Git 工作时间，也不要求填写会议或沟通记录。

### 7.5 假设与待验证项

- 大多数需要填写的日报工作都能被 Git 提交合理代表。
- 用户愿意把 API Key 留在本机，以换取更灵活的 Provider 选择。
- 常用项目数量通常不超过 20 个，扫描和预览性能足够。
- PMS 返回的项目、任务和工时类型足以构造提交所需字段。
- 用户愿意自行完成项目、任务和加班工时确认，以保证与实际工时一致。

## 8. 发布计划

### M1：本地 Git 复盘基础

完成日报页面骨架、Git 项目/作者管理、Git 提交采集与预览，以及 PMS 待填日期、项目、任务和工时类型读取。此阶段不调用 AI，用户可验证数据和工时分配流程是否正确。

### M2：AI 报告闭环（已完成）

接入 Provider 与模型配置，支持生成、编辑、PMS 工时条目配置和直接提交；概览页加入“今日工作”卡片。这是可日常使用的首个版本。

### M3：PMS 配置与状态回读（已完成）

补充 PMS Token 配置、提交结果记录和当月日报状态刷新；提供从 GitReport 导入 Git 项目配置的显式操作。

### 后续候选项

- 从 Git diff 提取更具体的工作描述。
- 将各 AI 平台的当日 Token 和成本与报告关联，形成“投入—产出”复盘。
- 可配置报告模板、项目标签和不同团队日报格式。
- 在托盘面板中显示“今日尚未生成日报”状态与快捷入口。
